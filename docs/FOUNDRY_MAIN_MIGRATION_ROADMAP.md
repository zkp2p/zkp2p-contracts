# Foundry Main Migration Roadmap

**Status:** Draft  
**Created:** 2026-03-12  
**Target branch:** `foundry-main`

## Goal

Migrate this repository from a Hardhat-first toolchain to a Foundry-only toolchain on a parallel `foundry-main` branch, then promote that branch to canonical `main` once parity and cutover gates are satisfied.

This is not a partial tooling refresh. The end state is:

- Forge is the only contract test runner.
- Foundry scripts are the only deployment path.
- Coverage is produced by `forge coverage`.
- Hardhat, `hardhat-deploy`, TypeChain, and `solidity-coverage` are removed.
- The current Hardhat test suite is fully represented in Foundry so test case coverage does not regress.

## Core Decisions

1. `foundry-main` is the migration integration branch.
2. `main` remains production-maintenance-only until cutover.
3. Existing Hardhat tests are the behavioral source of truth.
4. Existing Foundry tests are not authoritative and may be rewritten or deleted.
5. No new Hardhat tests or deploy scripts should be added after this roadmap starts, except for emergency production fixes that must land before cutover.

## Success Criteria

The migration is complete only when all of the following are true:

- Every current Hardhat test file has a mapped Foundry replacement.
- Every materially distinct test case from the Hardhat suite exists in Foundry.
- The Foundry suite passes in CI across unit, integration, fuzz, invariant, and fork lanes.
- Deployment flows currently handled by `deploy/*.ts` are replaced with Foundry scripts or intentionally archived as obsolete.
- Coverage is generated by Foundry and no longer blocks normal developer iteration on every push.
- No package, script, or downstream workflow still requires Hardhat artifacts, TypeChain output, or `hardhat-deploy`.
- Hardhat config, plugins, and TS deployment/tests can be deleted without losing protocol capability.

## Operating Rules

### Branch Strategy

- Create a long-lived `foundry-main` branch from the current `main`.
- All migration work targets `foundry-main`.
- Short-lived feature branches should branch from `foundry-main`, not `main`.
- `main` accepts only:
  - production hotfixes
  - deployment-critical fixes
  - changes required to keep the current deployed system operational
- Hotfixes merged into `main` must be merged into `foundry-main` immediately.

### Freeze Policy

Once `foundry-main` starts:

- Do not add new Hardhat unit tests.
- Do not add new `hardhat-deploy` scripts.
- Do not expand TypeChain usage.
- Do not improve the rushed Foundry suite in place unless the work directly supports the authoritative migration plan.

### Source-of-Truth Policy

For migration purposes:

- Hardhat tests define required behavior.
- Foundry tests must match or exceed that behavior.
- Existing Foundry tests are disposable unless explicitly retained.

## Phase Plan

### Phase 0: Bootstrap and Freeze

**Objective:** establish migration lanes and stop the Hardhat surface from growing.

Deliverables:

- Create `foundry-main`.
- Add this roadmap and the parity matrix.
- Update contributing guidance so new tests target Foundry.
- Mark current Foundry tests as provisional.
- Decide whether `main` or `foundry-main` remains the default GitHub branch during migration.

Exit criteria:

- `foundry-main` exists.
- All new migration PRs target `foundry-main`.
- Team agrees Hardhat is in maintenance mode only.

### Phase 1: Baseline and Mapping

**Objective:** build the exact migration ledger before rewriting tests.

Deliverables:

- Enumerate every Hardhat test file and assign a target Foundry file.
- For each Hardhat file, record:
  - setup style
  - contracts under test
  - positive paths
  - revert paths
  - event assertions
  - state transition assertions
  - edge cases
- Mark which tests are:
  - straight ports
  - ports that should be split into multiple Solidity test contracts
  - obsolete because the underlying deployed contract family is intentionally retired

Exit criteria:

- No Hardhat file is unmapped.
- There is explicit reviewer agreement on what counts as "1:1 parity" per file.

### Phase 2: Foundry Test Foundation

**Objective:** build the reusable Solidity-side testing primitives before mass porting.

Deliverables:

- Shared Foundry fixture builders for:
  - account setup
  - token minting and approvals
  - registry wiring
  - escrow/orchestrator deployment
  - common constants and hashing helpers
  - signature and attestation helpers
- Shared assertion helpers where they reduce duplication.
- Stable naming conventions for:
  - unit
  - integration
  - fuzz
  - invariant
  - fork

Rules:

- Do not port tests one-off with duplicated setup if the setup pattern will recur.
- Do not optimize for cleverness. Optimize for transparent, repetitive harnesses that are easy to review and easy for AI agents to extend.

Exit criteria:

- At least two representative Hardhat suites can be ported cleanly without inventing new harness structure each time.

### Phase 3: Straight Port of the Deterministic Suites

**Objective:** migrate the hand-crafted example-based Hardhat suite with no case loss.

Recommended order:

1. `libs`
2. `registries`
3. `unifiedVerifier`
4. `hooks`
5. `periphery`
6. `rateManager`
7. `escrow`
8. `orchestrator`
9. `escrowV2`
10. `orchestratorV2`
11. `deploy`
12. `patchCoverage`

Per-suite requirements:

- Preserve all existing behavioral cases.
- Keep revert coverage.
- Preserve event assertions where behavior depends on them.
- Preserve cross-contract wiring assertions from deployment tests.
- Improve naming and fixture quality only if behavior stays equivalent or stricter.

Deletion rule:

- A Hardhat test file may be removed only after:
  - its Foundry replacement exists
  - parity is marked complete in the matrix
  - CI has passed with the Foundry replacement

Exit criteria:

- Every deterministic Hardhat test file has a passing Foundry replacement.

### Phase 4: Rebuild Fuzz, Invariant, and Fork Coverage

**Objective:** replace the rushed Foundry-specific suite with intentional Foundry-native property testing.

Deliverables:

- Rewritten fuzz tests for critical value flows.
- Rewritten invariants for escrow/orchestrator/accounting properties.
- Rewritten fork tests for network-specific hooks or oracle integrations.

Rules:

- Do not treat the current Foundry fuzz/invariant suite as authoritative.
- Use the deterministic ports from Phase 3 to identify missing properties worth promoting into fuzz or invariants.

Exit criteria:

- Property-based coverage is stronger than the original mixed Hardhat/Foundry state.

### Phase 5: Deployment Migration

**Objective:** remove `hardhat-deploy` and move operational deployment flows into Foundry scripts.

Scope:

- Port active deployment scripts from `deploy/*.ts` into `script/*.s.sol`.
- Preserve:
  - deployment ordering
  - constructor arguments
  - registry configuration
  - ownership transfers
  - verification flows
  - environment-driven network configuration

Rules:

- Historical one-off scripts that are no longer operationally needed should be explicitly marked as archived, not silently dropped.
- Deployment script migration should prefer composable Solidity scripts over giant monoliths.

Exit criteria:

- All active deployments can be performed and replayed through Foundry scripts.
- Hardhat deployment tests have Foundry equivalents.

### Phase 6: CI Reshape

**Objective:** stop slow coverage from dominating iteration and make Foundry the default CI path.

Target CI structure:

- PR fast lane:
  - `forge build`
  - deterministic unit/integration suites
  - selected fast fuzz smoke runs
- PR extended lane:
  - targeted fork tests where needed
- Nightly or pre-merge lane:
  - full fuzz
  - full invariants
  - full coverage

Rules:

- Do not run full coverage on every push unless the repo proves it can finish fast enough to preserve developer iteration.
- Coverage should inform quality, not throttle all development by default.

Exit criteria:

- Hardhat CI jobs are gone or disabled on `foundry-main`.
- Coverage is generated by Foundry.
- PR iteration time is materially lower than the current Hardhat-plus-coverage model.

### Phase 7: Hardhat Retirement

**Objective:** delete obsolete tooling only after parity and operational readiness are proven.

Remove only after all prior phases are complete:

- `hardhat.config.ts`
- Hardhat plugins from `package.json`
- `deploy/*.ts`
- `tasks/*.ts`
- `test/**/*.ts`
- TypeChain generation and output
- `solidity-coverage`
- Hardhat-specific CI workflows

Exit criteria:

- A clean clone of `foundry-main` can compile, test, deploy, and produce coverage without Hardhat installed.

### Phase 8: Branch Cutover

**Objective:** make `foundry-main` the canonical branch.

Cutover checklist:

- Foundry CI is stable.
- Deployment scripts are production-ready.
- Test parity matrix is fully checked off.
- Downstream consumers no longer need Hardhat artifacts or TypeChain.
- Team agrees no critical operational path still depends on Hardhat.

Possible cutover moves:

- Rename `main` to `main-legacy-hardhat`.
- Rename `foundry-main` to `main`.
- Freeze or archive the legacy branch after a defined support window.

## Test Parity Protocol

This protocol is mandatory. It is the main control against silent regression.

### Definition of 1:1 Parity

For each Hardhat source file:

- every distinct success path must exist in Foundry
- every distinct revert path must exist in Foundry
- every critical event expectation must exist in Foundry when behavior depends on it
- every important state transition assertion must exist in Foundry
- every constructor or deployment wiring assertion must exist in Foundry

The Foundry port may:

- split one TS file into multiple Solidity test contracts
- use cleaner fixtures
- add additional cases
- promote deterministic cases into fuzz tests

The Foundry port may not:

- silently drop edge cases
- silently weaken revert checks
- replace exact assertions with vague broader checks

### Required Workflow Per Test File

1. Read the Hardhat file.
2. Extract the case list into the parity matrix.
3. Implement the Foundry port.
4. Mark each case as:
   - ported
   - improved
   - intentionally omitted with rationale
5. Run the relevant Foundry suite.
6. Only then remove or archive the Hardhat file.

### Review Rule

Every PR that removes a Hardhat test file must link its parity-matrix row updates.

## Recommended Work Breakdown

The repo should be migrated in slices that keep reviewable diffs:

- PR series 1: roadmap + parity matrix + CI freeze
- PR series 2: Foundry fixtures/helpers
- PR series 3: registries + libs + unified verifier
- PR series 4: hooks + periphery + rate manager
- PR series 5: escrow + orchestrator
- PR series 6: v2 escrow/orchestrator
- PR series 7: deploy/system tests
- PR series 8: Foundry fuzz/invariants/forks rewrite
- PR series 9: Foundry deployment scripts
- PR series 10: CI cutover
- PR series 11: Hardhat removal

## Risks

### Risk: false confidence from incomplete test ports

Mitigation:

- enforce the parity matrix
- ban direct deletion of Hardhat tests without mapped Foundry replacements

### Risk: deployment behavior drift during script migration

Mitigation:

- port deploy tests after each deployment script family
- preserve constructor/config assertions explicitly

### Risk: downstream dependency on Hardhat artifacts

Mitigation:

- inventory all artifact consumers early
- replace them before Hardhat removal

### Risk: migration branch diverges too far from production fixes

Mitigation:

- merge `main` into `foundry-main` frequently
- keep `main` on maintenance-only rules

## First Execution Steps

The first practical PR on `foundry-main` should do only this:

1. Add this roadmap.
2. Add the parity matrix scaffold.
3. Update CI so coverage is not on the critical path for every push.
4. Add Foundry helper scaffolding.
5. Declare a Hardhat freeze for non-hotfix work.

That keeps the first move administrative and reversible, while setting up the migration to proceed in disciplined slices.
